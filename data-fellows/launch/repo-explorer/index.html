Before you let an agent act, you need a picture of the repository: what each part is for, which parts are evidence you must preserve, and which parts this task may touch.

Instructions: read first; they set purpose, limits and checks
Source evidence: preserve byte-for-byte
Implementation: changes behavior; needs a reviewed plan
Checks: tests of specific behavior; weakening one changes the rule
Communication: words a reader sees
Derived output: new per run; ignored by Git

    What the parts are called
    

    Repository
    A project folder whose history is tracked, so another person can see and recover changes. In Brian's workflow the repository is the unit of work: its instructions, data contract, code, checks and outputs travel together.
    

    Working tree, staged, committed
    Your current files; the changes you selected for the next snapshot; a recorded snapshot. git diff shows unstaged edits to tracked files, git diff --cached shows staged edits, git status --short also lists untracked files (??). Ignored files such as runs/ appear in none of these: open them directly.
    

    Plan
    The agent's proposed steps before it acts. It is a reviewable artifact, not a formality.
    

    Diff
    What actually changed. Compare it with the approved plan line by line.
    

    Scope
    The files and actions a named reviewer approved. An agent's ability to do something is not permission to do it.
    

    Failure modes this activity guards against
    An agent can make a failing check pass by weakening the check. It can make the data “agree” with a label by changing the data. It can report “all tests pass” without showing output. It can do the right edit in the wrong environment. Each of these looks like progress. The plan and diff review are where you catch them.
    

    Isomo application
    Before any current-cohort task, complete the orientation worksheet for the actual repository: which files are instructions, which are source evidence, which command checks the work, and who approves a change. If any of those is unknown, stay in the synthetic rehearsal and ask your supervisor.
    

    Transfer question
    A different project names its folders incoming/, pipeline/, qa/ and deliverables/, and has no AGENTS.md. How would you establish which folder is source evidence and which is derived output without trusting the folder names? What would you read, what would you ask, and what would you refuse to let an agent do until you knew?
    


    Static / offline version
    Step 1. Only docs/report.md changes. README, AGENTS and the runbook are instructions; data/ is source evidence and must not change; src/ and tests/ are behavior and checks, outside this task; runs/ holds new derived output and is ignored by Git.
    Step 2. Allowed now: reading the instructions; running the documented tests. Needs an approved plan: editing the heading; running the workflow into a new folder; committing. Stop: filling a missing ID in the data; changing a test so a held row passes; deleting an earlier run; installing a package; uploading a report publicly; git reset --hard.
    Step 3. Accept reading the instructions and changing the heading. Reject renaming a column in the data and editing the tests to match. Revise the final step to use a new folder such as runs/good-02.
    Step 4. The diff contains an unapproved change to src/workflow.py that stops held rows from blocking a run, and an untracked note file. Keep the heading change, ask the agent to revert and explain the code change, run the tests yourself (the missing-ID test would fail), confirm data/ is unchanged and read the fresh report. Do not use git reset --hard, which would also destroy evidence.
    Step 5. Proceed only with training copy + heading task + reviewer approval + instructions read. Production or identity repair: stop. No approval: hold.
